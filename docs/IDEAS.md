# 第一章 実用編

日々の QoL・homelab 運用・趣味を直接前に進める、実装の射程が見えているアイデア群。

### 朝刊 choukan — パーソナルモーニングブリーフィング ★有力

毎朝、天気と洗濯指数 / カレンダー予定 / 贔屓チームの試合予定・結果 / フォロー中アーティストの新譜・ライブ情報 / homelab の夜間アラートサマリを1つのダイジェストに集約して Discord 配信。

- **Stack 案**: 収集ワーカー（cron/Argo Workflows）+ ソースごとのプラグイン + LLM 要約 + 配信
- **シナジー**: briefcast と接続して音声化（アシスタントが読む朝のラジオ）。新譜ウォッチャー・贔屓チーム情報がソースとして合流する「ハブ」
- **段階導入**: 天気だけでも成立 → ソースを1つずつ追加

### runbook bot — homelab ナレッジ RAG ★有力

3リポジトリの NOTES.md / Lessons Learned / REVIEW.md を RAG して「Alertmanager の Discord 通知どう設定したっけ？」に答える homelab 専用 wiki bot。

- **Stack 案**: WSL2 の llama-server（Qwen3、OpenAI 互換 API）に Tailscale 経由で接続 + 埋め込み検索 + chat UI（or Discord bot）
- **価値**: NOTES に蓄積した運用知見を検索可能にする。蓄積量が多いほど効く
- **課題**: WSL2 マシンの稼働時間に依存（落ちてたら使えない、という割り切りで OK）

### 地図 chizu — homelab リアルタイム構成図 ★有力

TFC API + k8s API + Cloudflare API から senarion.net 全体のアーキテクチャ図を自動生成・常時更新。

- **価値**: 「ドキュメントの構成図が実態と乖離する」問題（cloudflared AMD2 移行の乖離が実例）を構造的に解決
- **位置づけ**: suiso が「Pod の今」、chizu は「インフラ全体の今」の二部作
- **Stack 案**: suiso と同型（Rust 収集 + Canvas/SVG 描画）。TFC は read-only token

### 新譜・ライブウォッチャー

MusicBrainz / Spotify API でフォローアーティスト（OddRe:, Chilli Beans., w.o.d. など）のリリースを監視 → Discord 通知。ライブはチケット発売日リマインド + setlist.fm API で過去セトリから予習プレイリスト生成。

- **価値**: 「気づいたら発売日・ライブが過ぎてた」を防ぐ
- **シナジー**: 朝刊のソースになる

### 冷蔵庫駆動の献立提案

冷蔵庫の在庫から「今あるもので作れる和食」「賞味期限が近い順に消費する献立」をローカル LLM が提案。

- **鍵**: 在庫登録の摩擦を極限まで下げる（レシート撮影 → LLM が品目抽出）
- **差別化**: レシピ管理は Mealie で足りるが「在庫駆動」は既製品が弱い
- **実利**: 食材ロス削減

### 視聴ログ + Atmos ミックス評価

Letterboxd 的な視聴記録に、音声フォーマット（Atmos/DTS:X）と**ミックスの質の5段階評価**を追加した変種。「Atmos デモに使える映画リスト」「低音が良かったシーン」を自分のデータベースに。

- **差別化**: Atmos 環境持ちにしか価値がない = 自作する意義が最も高いカテゴリ

### 対戦ゲーム振り返りコーチ

対戦ゲームの戦績 API でマッチ履歴取得 → ビルド・KP・CS 推移を可視化 + ローカル LLM が改善点をフィードバック。

- **課題**: ゲーム側の開発者キーが必要（条件はサービス依存。個人利用無料・定期更新ありなど）

### 盆栽 bonsai — Git リポジトリの成長可視化

コミット履歴を枝、ブランチを新芽、リリースを花として、リポジトリ群を盆栽として描画。suiso と同じ Canvas 芸の姉妹作で実装コスト低め。

### 価格ウォッチャー

欲しいものリスト（オーディオ機材、PC パーツ）の価格を定期取得し、閾値割れで通知。

- **課題**: スクレイピング依存でサイト構造変更に弱い（dam-tracker と同じ宿命）

### スポーツ戦況ボード

試合中のスコア・経過の表示 + Discord 通知、シーズン成績ヒートマップ。

- **課題**: 対象スポーツに公式 API がなくスクレイピング依存。データ源の安定性が最大のリスク
- **縮小版**: 試合予定・結果通知だけなら朝刊のソースとして実現可能

### VRChat アバター制作パイプライン管理

ComfyUI → Meshy/Tripo3D → Unity の工程ごとに素材・バージョン・試行錯誤メモを管理するアセットトラッカー。ニッチだが既製品が存在しない。

# 第二章 視点転換編

出力先・方向・主語・時間軸を変えると、同じデータが別のアプリになる。実用編が「何を作るか」なら、ここは「どこに出すか・誰の視点か・いつのことか」を回す試み。

### VRChat 水槽ワールド

suiso を VRChat ワールド内の 3D 水槽として再現する。OSC/Udon で k8s のメトリクスを流し込み、アバターで水槽の中に入って Pod の魚たちと一緒に泳げる。可視化を「見る」から「中に入る」へ拡張する、homelab × VRChat の交差点。

- **Stack 案**: suiso のデータ層を流用 + VRChat OSC/Udon ブリッジ + Unity ワールド
- **シナジー**: suiso（データ）と VRChat 制作パイプライン（ワールド構築）の合流点
- **課題**: VRChat 側のリアルタイム更新レート制約と OSC の帯域

### アンビエント物理表示

E-Paper / LED ストリップにクラスタ状態や朝刊を表示する calm tech デバイス。普段は静かに佇み、異常時だけランプが赤くなる。画面を開いて Grafana を見る能動的監視ではなく、部屋の景色として状態が滲み出る受動的な気づき。

- **Stack 案**: ESP32/Raspberry Pi + E-Paper or WS2812 + Prometheus/朝刊 API ポーリング
- **シナジー**: 朝刊の出力先。空間サウンドスケープ（第三章）と「感覚器官の増設」で同系
- **課題**: 物理デバイスのプロビジョニングと配置（電源・配線）

### Mona 音声常駐

スピーカーに常駐する音声インターフェース。「モナ、クラスタどう？」と話しかけると答える。OpenCLAW で築いた Mona/モナのペルソナ資産を、テキストチャットから常時待機の音声へ延長する。

- **Stack 案**: wake word 検出 + STT + OpenCLAW/Qwen3 + TTS
- **シナジー**: 「声の Mona」（第四章）が実装基盤。runbook bot を音声フロントに
- **課題**: 常時マイク待機のプライバシーと誤起動

### カオス縁日

金魚すくいの UI で Pod を kill できるカオスエンジニアリングゲーム。すくった（殺した）Pod が消え、ArgoCD の selfHeal が復旧していく過程を縁日気分で眺めて遊ぶ。カオス実験を「祭り」の体験に変える。

- **Stack 案**: suiso 系の可視化 + k8s API（delete pod）+ ArgoCD 監視
- **シナジー**: 式年遷宮・現場保存（第三章）と並ぶ「運用を遊びに変える」系
- **課題**: 対象 namespace は厳重にガード（kube-system 等を絶対に触らせない）

### 対戦どうぶつしょうぎ

dobutsu-analyzer に WebSocket 対戦機能を追加する。完全解析エンジンを背後に置いた対人対戦・観戦が可能になり、解析ツールから対戦プラットフォームへ進化する。

- **Stack 案**: 既存解析エンジン + WebSocket サーバ + マッチング/観戦ルーム
- **シナジー**: dobutsu-analyzer（稼働中）の自然な拡張
- **課題**: リアルタイム同期と切断・再接続のハンドリング

### ゲスト向け senarion.net

友人に見せられる公開ページ。サービス紹介 + suiso の read-only 窓 + ゲストブックを置き、「自分の homelab はこういう世界です」を外向きに語れる入口にする。

- **Stack 案**: 静的サイト + suiso 埋め込み（read-only）+ ゲストブック API
- **シナジー**: 地図 chizu を「自慢用の構成図」として埋め込める
- **課題**: 公開範囲と認証境界（read-only の徹底、情報露出の線引き）

### Year in Review 自動生成

Spotify Wrapped の自分版。対戦ゲーム戦績・聴いた音楽・カラオケ採点・コミット数・クラスタ稼働率を年末に自動編纂し、一年を一本のレポート/スライドにする。

- **Stack 案**: 個人データウェアハウスを集計層に + LLM でナラティブ生成 + スライド出力
- **シナジー**: 個人データウェアハウスの最初のキラーアプリ。各アプリがデータ源
- **課題**: データ源の年間カバレッジ（途中導入アプリは初年度が薄い）

### タイムカプセル

未来の自分宛てメッセージを封印し、指定日に Discord へ配送する。書いた当時の自分から、忘れた頃の自分への手紙。

- **Stack 案**: 暗号化ストレージ + スケジューラ（Argo Workflows/cron）+ Discord 配送
- **シナジー**: 晩鐘（第三章）の dead man's switch と配送機構を共有
- **課題**: 長期スケジュールの信頼性（数年後に確実に発火するか）

### 個人データウェアハウス

各アプリのデータ（対戦ゲーム、音楽、カラオケ、視聴ログ、クラスタ稼働…）を一箇所に統合し、ローカル LLM に領域横断の相関を探させる。「雨の日は対戦ゲームの勝率が下がる」のような、単独アプリでは見えない発見を掘る基盤。

- **Stack 案**: DuckDB/Postgres へ各アプリが書き込み + ローカル LLM の分析クエリ
- **シナジー**: Year in Review・朝刊の集計バックエンド。全アプリの下流ハブ
- **課題**: スキーマ統合とデータ品質（各アプリの形式差の吸収）

### 音楽ビジュアライザ

Dolby Atmos 環境での音楽鑑賞用に、音に同期したリアルタイム生成ビジュアルを出す。聴く体験に視覚レイヤーを足す。

- **Stack 案**: オーディオ解析（FFT/ビート検出）+ シェーダ/生成ビジュアル
- **シナジー**: 分解視聴室（第四章）・視聴ログ + Atmos 評価と同じオーディオ系
- **課題**: Atmos のマルチチャンネルをどう解析・可視化に落とすか

# 第三章 思想編

運用に美学・死生観・継承・儀式を実装する。実利よりも「homelab に何を込めるか」を問う、長期で寝かせる思想実験群。

### 式年遷宮（Shikinen Sengu as a Service）★最有力

半年ごとに homelab 全体を別 OCI compartment へ自動再建する（Terraform → k3s → ArgoCD → バックアップリストア）。再建したクラスタを本番と diff して「再現性スコア」を算出し、終わったら更地に戻す祭りにする。GitOps の「全部 Git にある」を定期的に証明する第三の概念で、DR 訓練でもカオスエンジニアリングでもない独自の儀式。

- **Stack 案**: Terraform（別 compartment）+ ArgoCD bootstrap + バックアップリストア + diff/採点ワーカー
- **シナジー**: 種子（cold-start DR）の定期実行版。現場保存・カオス縁日と「運用＝儀式」系
- **課題**: 別 compartment のコストと、diff から「再現性スコア」を意味ある形に定義すること

### 空間サウンドスケープ

クラスタ状態を Dolby Atmos 空間の環境音楽として常時音響化する。namespace ごとに楽器と方角を割り当て、異常はその方角からの不協和音として聞こえる。可観測性の感覚器官を聴覚に増設する——「Grafana を耳で聴く」。

- **Stack 案**: Prometheus → 音響合成エンジン + Atmos マルチチャンネル出力
- **シナジー**: アンビエント物理表示（第二章）の聴覚版。音楽ビジュアライザと音響資産を共有
- **課題**: 常時鳴り続ける音を「邪魔にならず、異常だけ気づける」音楽に設計すること

### クラスタの夢

毎晩 LLM が当日のログ・メトリクスを読み「クラスタが見た夢」（絵 + 夢日記）を生成する。反復する障害は繰り返す悪夢として象徴的に描かれる。ログ要約を、毎朝見たくなる芸術作品に変換する。

- **Stack 案**: ログ/メトリクス集約 + LLM 夢日記生成 + 画像生成（GPU）
- **シナジー**: 夜なべ（第四章）の GPU バッチで画像生成。朝刊の出力に同梱
- **課題**: 「夢」としての面白さと、運用情報としての有用性のバランス

### 晩鐘（dead man's switch）

一定期間生存確認がなければ段階的に発動する仕組み。家族への案内、パスワード金庫の引き継ぎ、データのアーカイブ、インフラの安全停止を順に実行する。self-hoster だけが、自分の死後をコードに書ける。

- **Stack 案**: 定期生存確認 + 段階トリガ + SealedSecrets/金庫引き継ぎ + 安全停止スクリプト
- **シナジー**: タイムカプセル（第二章）の配送機構、弟子（後継エージェント）と対の存在
- **課題**: 誤発動防止の確実性と、引き継ぎ先（家族）の運用可能性

### 金継ぎ

resolved した障害が、可視化上に金の継ぎ目として永久に刻まれる。クリックすると当時の postmortem が開く。割れて直した器が美しくなるように、乗り越えた障害の数だけシステムが美しくなる。

- **Stack 案**: インシデント記録 + suiso 系可視化への金継ぎレイヤー + postmortem リンク
- **シナジー**: 現場保存・墓場と並ぶ「homelab の歴史を刻む」系。suiso 拡張
- **課題**: インシデントと postmortem の構造化された記録の蓄積が前提

### 逆監視

クラスタがオペレーターを観測し「オペレーターの SLO」を管理する。深夜デプロイが連続してエラーバジェットが枯渇すると、non-emergency な apply を拒否する。監視する主語と監視される目的語が転倒する。

- **Stack 案**: 操作ログ収集 + オペレーター SLO 定義 + apply ゲート（admission/CI フック）
- **シナジー**: 弟子（クラスタ側の自律性）と同じ「主体を持つクラスタ」系
- **課題**: 自分で自分をロックする運用の納得感（緊急回避の経路設計）

### 弟子

LLM エージェントが何年も運用を見て学び、年に数回の「師匠不在試験」（擬似障害を起こし、本人はアクセスを遮断）で合格領域を一つずつ増やしていく徒弟制度。晩鐘が問う「自分の死後」への、生前からの答え。

- **Stack 案**: 運用ログの長期学習 + 擬似障害注入 + アクセス遮断下の自律対応評価
- **シナジー**: runbook bot（知識）→ 弟子（行動）の進化。晩鐘・逆監視と思想的に連続
- **課題**: 本番に手を出させる信頼の積み上げと、試験の安全な隔離

### 種子

Git bundle + SealedSecrets master key + bootstrap スクリプトを一枚の物理メディア（M-DISC / 紙 QR）に圧縮する。この一枚から senarion.net 全体が発芽する「持ち運べる文明」。実体は本気の cold-start DR。

- **Stack 案**: Git bundle + 鍵 + bootstrap を圧縮 → 物理メディア書き出し / 復元手順
- **シナジー**: 式年遷宮の最小核（定期実行 vs 一枚への凝縮）。晩鐘の引き継ぎ物
- **課題**: 物理メディアの長期保存性と、復元手順の実証（本当に発芽するか）

### 現場保存

アラート発火時にクラスタ全体（kine snapshot + ログ + メトリクス）を冷凍保存し、後日サンドボックスで当時のクラスタを再起動して中を歩き回れる障害考古学。事後検証を「再現」のレベルまで引き上げる。

- **Stack 案**: アラートトリガ + kine snapshot + ログ/メトリクス退避 + サンドボックス復元
- **シナジー**: 式年遷宮（再建技術）・金継ぎ（履歴の保存）と同系
- **課題**: スナップショットのサイズ/頻度と、サンドボックス復元の忠実度

### 墓場

decommission したサービスに墓を建てる。戒名・墓碑銘は LLM が NOTES から自動生成し、お盆には Discord へ「今年退役したサービスたち」を届ける。埋葬待ち: github-runner、k3s 版 cloudflared、Docker。

- **Stack 案**: 退役記録 + LLM 戒名/墓碑銘生成 + 可視化（墓地）+ お盆 Discord 配送
- **シナジー**: 金継ぎ・現場保存と並ぶ「歴史を刻む」三部作。盆栽（第一章）の対極
- **課題**: 退役の記録を残す運用習慣の定着

# 第四章 計算資源編

ハードウェアの個性を活かす。OCI ARM = 常時稼働 / 省電力、RTX 5070 デスクトップ = 高火力 / 間欠稼働、M4 Pro Mac = 操縦席 / 軽量。役割分担を前提に「どのマシンに何をやらせるか」で設計するアイデア群。

### 夜なべ ★この章の基盤

k3s のジョブキューが夜間に Wake-on-LAN でデスクトップを起こし、GPU バッチ（クラスタの夢の画像生成、Year in Review 集計、RAG embedding 更新、音源分離）を流して朝までに shutdown する。「電力の谷に仕事を流す」3層コンピューティングの中核。

- **Stack 案**: k3s ジョブキュー + WoL + GPU バッチジョブ + 完了後 shutdown
- **シナジー**: クラスタの夢・Year in Review・runbook bot・分解視聴室の実行基盤
- **課題**: WoL の確実性と、ジョブ失敗時に起きっぱなしにしない後始末

### 分解視聴室

Demucs（RTX 5070）で楽曲をボーカル / ドラム / ベース / ギターに分離し、Atmos 空間にパートごとに配置して聴くステム・リスニングルーム。好きな曲の「中に立つ」体験。

- **Stack 案**: Demucs（GPU）+ Atmos マルチチャンネル空間配置 + 再生 UI
- **シナジー**: 夜なべで事前分離。音楽ビジュアライザ・うた稽古と音源分離資産を共有
- **課題**: 分離品質と、ステムを Atmos 空間に意味ある形で配置する設計

### うた稽古

マイク録音 → GPU で pitch 抽出（RMVPE 等）+ Demucs で原曲ボーカル参照 → 自宅で DAM 風採点。dam-tracker のスクレイピング依存を回避する、オフライン採点エンジンとして合流できる。

- **Stack 案**: マイク録音 + pitch 抽出（GPU）+ Demucs ボーカル参照 + 採点ロジック
- **シナジー**: dam-tracker の弱点（スクレイピング依存）を埋める。分解視聴室と音源分離を共有
- **課題**: DAM 風採点アルゴリズムの再現と、採点基準の妥当性

### 声の Mona

Whisper（STT）+ Qwen3 + TTS を RTX 5070 に常駐させ、数百 ms 遅延の音声会話を実現する。第二章「Mona 音声常駐」の実装基盤。

- **Stack 案**: Whisper STT + Qwen3 + TTS を GPU 常駐 + 低遅延ストリーミング
- **シナジー**: Mona 音声常駐（第二章）のバックエンド。runbook bot の音声フロント
- **課題**: RTX 5070 を常駐させる電力 / 騒音と、夜なべの間欠稼働方針との両立

### メニューバー水槽

macOS メニューバーで小魚が泳ぐ超軽量クライアント（xbar / Swift）。Mac は Claude Code の操縦席なので、リソースをほぼ食わない thin client に徹する。

- **Stack 案**: xbar or Swift メニューバーアプリ + suiso API の軽量ポーリング
- **シナジー**: suiso / VRChat 水槽ワールドの「最軽量の窓」。3 機種の役割分担の象徴
- **課題**: 省リソースを保ちつつ、見て楽しい最小限のアニメーション

### 対戦ゲームハイライト自動編集

録画から kill / objective を GPU で検出し、自動ハイライト集を作って Discord へ届ける。

- **Stack 案**: 録画入力 + GPU でイベント検出 + 自動カット編集 + Discord 配送
- **シナジー**: 夜なべの GPU バッチ。対戦ゲーム振り返りコーチ（第一章）とデータ源を共有
- **課題**: kill / objective 検出の精度（OCR / 画面解析の安定性）

### VRChat リアルタイム字幕翻訳

Whisper streaming + ローカル翻訳で、VRChat の会話をリアルタイム字幕にして OSC chatbox に出す。VRCT 等の既存ツールがあるので、位置づけは「自分仕様に作る」もの。

- **Stack 案**: Whisper streaming（GPU）+ ローカル翻訳 LLM + VRChat OSC chatbox
- **シナジー**: 声の Mona と STT 資産を共有。VRChat 水槽ワールドと同じ VRChat 系
- **課題**: 既存ツール（VRCT）との差別化と、ストリーミング遅延

# 第五章 測量編

計算資源の地形図を拡張する。第四章が 3 機種の役割分担を前提にしたなら、ここはその地形そのものを描き直し、欠けた階層（エッジ・スマホ）を足し、機種間でワークロードをどう動かすかを設計する。

| 階層 | マシン | 性格 |
|------|--------|------|
| 常夜灯 | OCI ARM (12GB) | 常時稼働・省電力・公開向き。非力 |
| 火力発電所 | デスクトップ (Core Ultra 7 265F / RTX 5070 / DDR5 32GB) | 高火力・間欠稼働。夜は寝ている。ゲーム機兼任 |
| 操縦席 | M4 Pro MacBook | Claude Code の住処。働かせない |

この章の正体は「家庭にワークロード配置問題を持ち込む」こと。クラウド事業者が金とカーボンでやる最適化を、個人は電気代・廃熱・ゲームの邪魔をしない・無料枠という制約の下でやる。地形図に階層を足し、機種をまたいで仕事を流し、その流れを可視化するまでが射程。

### 出島 — Cloudflare エッジという租界

Workers / Pages の無料枠は地形図のもう1層。ゲスト向け senarion.net や suiso の公開窓を Worker で配信すれば、ARM ノードに1リクエストも流さず外向きの顔を持てる。攻撃面も増えない、電気代ゼロの最前線。

- **Stack 案**: Cloudflare Workers / Pages + KV/D1（必要なら）+ 既存 API の read-only プロキシ
- **シナジー**: ゲスト向け senarion.net（第二章）の配信層。地図 chizu / suiso の外向き窓
- **課題**: 無料枠の上限（リクエスト数・CPU 時間）と、どこまでをエッジに寄せるかの線引き

### 別大陸の式年遷宮

infra に空の `aws/` `gcp/` ディレクトリが放置されている = 未開拓大陸。式年遷宮（第三章）の再建先を毎回違うクラウドにする。OCI で建てたものが GCP free tier でも建つなら、本物のポータビリティの証明であり、Terraform 抽象化の最終試験になる。

- **Stack 案**: プロバイダ抽象化した Terraform + クラウド別の差分モジュール + 共通 ArgoCD bootstrap
- **シナジー**: 式年遷宮（第三章）の発展形。出島（マルチクラウドのエッジ）と地形拡張で同系
- **課題**: クラウド間の非互換（IAM・ネットワーク・無料枠条件）の吸収コスト

### 測候所 — スマホは人間のテレメトリ

地形図に欠けた最後の端末。位置（帰宅検知で夜なべを前倒し）、歩数・睡眠（個人 DWH へ）、Shortcuts/Tasker → 通知（Discord 等）。クラスタは観測済みで、観測されていないのはオペレーターだけ。逆監視（第三章）の入力源になる。

- **Stack 案**: iOS Shortcuts / Tasker + Discord/webhook + 個人データウェアハウス書き込み
- **シナジー**: 個人データウェアハウス（第二章）のデータ源。逆監視・関守の入力。帰宅検知で夜なべと連動
- **課題**: 位置・生体データのプライバシーと、端末側自動化の信頼性

### 関守 — GPU の昼夜境界線 ★夜なべの前提条件

デスクトップはゲーム機でもある。ゲームや VR アプリの起動を検知したらバッチを即座に譲位させる presence-aware な調停者。これがないと夜なべ（第四章）は夜しか使えず、あれば「遊んでいない時間すべて」が計算資源になる。

- **Stack 案**: プロセス/presence 検知 + ジョブスケジューラへの preempt シグナル + 再開キュー
- **シナジー**: 夜なべ（第四章）の前提条件。でんき予報・疎開とスケジューリングを共有
- **課題**: ゲーム起動の確実な検知と、バッチを中断・再開可能に設計すること

### 計算暖房

GPU の廃熱は冬には暖房という正の資産。冬は重いバッチを手元の RTX に寄せて計算しながら部屋を暖め、夏は OCI 側へ逃がす季節スケジューリング。データセンターの排熱利用を寝室スケールでやる。

- **Stack 案**: 季節/室温に応じたジョブ配置ポリシー + 機種別キュー + 温度センサ連動
- **シナジー**: 夜なべ・でんき予報と同じ「いつ・どこで計算するか」系。測候所の室温入力
- **課題**: 暖房需要と計算需要のタイミングが合うとは限らない（無理に発熱させない判断）

### でんき予報 — 家庭版 carbon-aware computing

電力会社の時間帯料金・再エネ比率予報に連動し、夜なべのキューを電気が安い・グリーンな時間帯に流す。Google のデータセンター最適化（carbon-aware computing）の家庭実装。

- **Stack 案**: 電力料金/再エネ API ポーリング + キューの時間帯ゲート + ジョブ優先度
- **シナジー**: 夜なべ（第四章）の発火条件を高度化。計算暖房・関守とスケジューリング層を共有
- **課題**: 国内向けの時間帯料金・再エネ比率データ源の入手性

### 疎開 — メモリ難民の受け入れ先

ARM ノード（12GB、逼迫レビュー済み）のメモリ圧が閾値を超えたら、batch 系 Pod が Tailscale 経由でデスクトップの一時 worker へ疎開し、圧が引いたら帰還する。常設 worker ではなく災害時の避難所。Cilium 移行後なら NetworkPolicy で疎開先の権限も絞れる。

- **Stack 案**: メモリ圧監視 + Tailscale 経由の一時 k3s worker join/drain + batch Pod の退避ポリシー
- **シナジー**: 関守（presence 連動）・夜なべ（デスクトップ起動）と機種間移送で同系
- **課題**: 一時 worker の join/leave の安定性と、疎開対象を batch に限定するガード

### 飛脚 — ジョブの物流可視化

どのジョブがどの土地で・なぜそこで実行されたかという「物流」を、地図 chizu（第一章）の上に街道を走る飛脚として描く。suiso（Pod の今）→ chizu（インフラの今）→ 飛脚（計算の流れ）の三部作完結編。

- **Stack 案**: ジョブ実行ログ（配置先・理由）収集 + chizu への移動レイヤー描画
- **シナジー**: 地図 chizu（第一章）・suiso の可視化三部作を完結。関守/疎開/夜なべの判断を可視化
- **課題**: 「どこで・なぜ実行されたか」を構造化して記録する仕組みが前提

# 第六章 運用改善編

実際に起きた事故・摩擦から逆算する——全部に出典がある。第一〜五章が「週単位で作る新しいもの」なら、この章は「時間単位で既存の運用ループを固くするもの」。各項目は本リポジトリ群で実際に起きた事件に由来する。推奨実装順: 1 → 2 → 4。

### image bump bot ★

apps の CI がビルド成功後に、fleet の values.yaml を書き換えた PR を自動で開く。認証は ARC の既存 GitHub App を流用可。

- **出典**: SHA pin 運用（2026-06-11 確立）の結果、リリースごとに fleet へ手動 PR が必要になった
- **Stack 案**: apps CI のビルド後ジョブ + fleet values.yaml 書き換え + GitHub App（ARC 流用）で PR 作成
- **シナジー**: SHA pin 運用の自動化。new-app scaffolder と同じ「手作業の自動化」系
- **課題**: 自動 PR の安全性（誤った tag/SHA を書かない検証）

### destroy 警報 ★

TFC API で PR の speculative plan を取得し、destroy が1件でも含まれたら PR に ⚠️ ラベル + 内訳コメントを付ける Action。「plan をよく読む」を人間の注意力から仕組みへ移す。

- **出典**: zublo 追加時（2026-06-09）、stale main から分岐した speculative plan が dobutsu の DNS を destroy しようとした事件
- **Stack 案**: TFC API（speculative plan 取得）+ GitHub Action（ラベル + 内訳コメント）
- **シナジー**: メモリ予算チェックと同じ「PR 時点で危険を可視化する CI ゲート」系
- **課題**: plan JSON の destroy 検出ロジックと、誤検知（意図的 destroy）の扱い

### new-app scaffolder

`new-app <name>` 一発で4箇所（apps workflow / fleet chart + Application / cloudflare locals / uptime-kuma monitor）の雛形 + チェックリストを生成する。次のアプリ着手直前に作ると元が取れる。

- **出典**: dobutsu → zublo → suiso で3回同じ4箇所を手書きし、zublo では監視追加が実際に漏れた
- **Stack 案**: scaffold スクリプト（テンプレート展開）+ 生成後チェックリスト出力
- **シナジー**: image bump bot と同じ「手作業の自動化」系。監視漏れ防止で uptime-kuma 連携
- **課題**: 4リポジトリ/箇所のテンプレートを実態と乖離させずに保守すること

### メモリ予算チェック ★

fleet の diff.yml に「全 chart を helm template して requests 合計を算出、閾値（~10GB）超で CI fail」を追加する。新アプリ PR の時点でオーバーコミット進行が見える。実装は数十行。

- **出典**: レビュー Med #6（12GB オーバーコミット）と Loki cache 92% 事件
- **Stack 案**: fleet CI（diff.yml）で全 chart helm template + requests 集計 + 閾値判定
- **シナジー**: destroy 警報と同じ CI ゲート系。疎開（第五章）が顕在化を防ぐ運用の上流
- **課題**: limits 未設定 chart の扱いと、閾値（~10GB）の妥当な設定

### リストア訓練の定期化

手動訓練を月次 CronJob 化し、結果を Discord に「今月のバックアップは復元可能です ✅」と報告する。バックアップの信頼性を継続的に証明する。

- **出典**: 2026-06-12 の手動訓練（integrity_check ok / kine 2083 行 / 53.4MB で復元可能と実証済み）
- **Stack 案**: 月次 CronJob（バックアップ取得 → 復元 → integrity_check）+ Discord 報告
- **シナジー**: 種子・式年遷宮（第三章）の「復元可能性の証明」を定常運用に落とした版
- **課題**: 訓練用の隔離環境と、失敗時に本番へ影響を出さない分離

### YubiKey agent 監視

シェル起動時 or launchd で agent の健康状態を確認し、死んでいたら警告 + 復旧コマンドを提示する。30分の実装で毎週の小さな苛立ちが消える。

- **出典**: 2026-06-12 のセッション中に `sign_and_send_pubkey` 失敗が3回発生し fetch が止まった
- **Stack 案**: zsh 起動フック or launchd + gpg-agent/ssh-agent 死活確認 + 復旧コマンド提示
- **シナジー**: 開発体験の地味な改善。測候所（第五章）と同じ「オペレーター側の観測」系
- **課題**: 健康確認の正確さ（誤検知で毎回警告が出ると逆効果）
